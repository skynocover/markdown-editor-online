# 分享連結的密碼加密

說明分享連結填了密碼之後，內容怎麼加密、為什麼這樣設計，以及它擋得住和擋不住什麼。程式在 [`src/share.js`](../src/share.js)。

## 一句話版本

**真正要保密的只有密碼。** salt 讓每條連結的 key 都不一樣，iv 讓每次加密的金鑰串流都不一樣，tag 讓竄改一定會被發現，PBKDF2 讓猜密碼變得很慢。

## 名詞一覽

| 名稱 | 是什麼 | 要保密嗎 | 這裡怎麼來 |
| --- | --- | --- | --- |
| 密碼 | 人記得住的字串 | ✅ | 使用者輸入 |
| salt | 隨機數，讓同一個密碼算出不同的 key | ❌ | 每次分享隨機 16 bytes |
| key（金鑰） | AES 真正使用的 256-bit 金鑰 | ✅ | 密碼 + salt 經 PBKDF2 算出，不會出現在連結裡 |
| iv / nonce | 隨機數，讓同一把 key 每次產生不同的金鑰串流 | ❌ | 每次隨機 12 bytes |
| 明文 | 要保護的內容 | ✅ | 壓縮後的 `{ name, content, readonly }` |
| 密文 | 加密後的結果 | ❌ | AES-GCM 輸出 |
| tag | 驗證碼，證明密文沒被改過 | ❌ | AES-GCM 輸出，附在密文最後 16 bytes |

不用保密的那幾個（salt、iv、密文、tag）全部放進連結。拿到連結的人什麼都有，只缺密碼。

## 整體流程

```
加密（分享端）
                 salt（隨機）
                    │
密碼 ──► PBKDF2 ×60 萬次 ──► key（256 bit）
                                 │
                 iv（隨機）──►  AES-GCM  ◄── 明文
                                 │
                            密文 + tag
                                 │
連結 = #e= base64url( salt | iv | 密文 | tag )


解密（打開端）
連結 ──► 拆出 salt、iv、密文、tag
密碼 + salt ──► PBKDF2 ──► 同一把 key
key + iv + 密文 ──► AES-GCM ──► 先驗 tag
                                 ├─ 對：輸出明文
                                 └─ 錯：直接失敗（密碼錯或連結被改過）
```

連結的資料放在 `#` 後面。瀏覽器不會把 `#` 之後的內容送到伺服器，所以主機看不到內容，加解密全部在瀏覽器裡完成。

## 第一步：密碼 → key（PBKDF2）

AES-256 需要剛好 32 bytes、看起來完全隨機的 key。密碼可能只有 `abc`，長度不對也不隨機，不能直接用。PBKDF2 把任意長度的密碼「攪拌」成一把格式正確的 key：

```
key = PBKDF2(密碼, salt, 600000 次, SHA-256)   → 固定 32 bytes
```

### 為什麼要跑 60 萬次

密文就在連結裡，攻擊者可以離線一直猜密碼。每猜一次都要跑 60 萬次 SHA-256（一般電腦約零點幾秒），正常使用者只解一次感覺不到，攻擊者要試幾億個密碼，成本就被放大 60 萬倍。60 萬次是 OWASP 2023 對 PBKDF2-SHA256 的建議值。

### salt 的作用

- 沒有 salt 的話，同一個密碼永遠算出同一把 key。攻擊者可以事先把常見密碼對應的 key 全部算好建表，拿到任何連結都直接查表。
- 有隨機 salt，就算密碼一樣，每條連結的 key 也不同：事先算好的表沒用，也沒辦法一次猜就破解多條，每條都得從頭猜。
- salt 不用保密，它的作用是讓每條連結都不一樣，不是當成秘密。

### 常見誤解：salt 會讓弱密碼變強？

**不會。** salt 就放在連結裡，攻擊者拿得到。假設密碼是 `123456`：

```
攻擊者：從連結拿到 salt
        PBKDF2("123456", salt, 600000) → 得到一樣的 key → 解開
```

攻擊者只要把常見密碼一個一個配上這條連結的 salt 算一遍，`123456` 前幾次就會猜中。salt 擋的是「事先算好、到處套用」，擋不住「對著這條連結直接猜」。

## 第二步：AES 與 GCM 模式

AES 是區塊加密：用 key 把 16 bytes 打亂成另外 16 bytes，key 對就能還原。內容不會剛好 16 bytes，而且同樣的區塊每次結果都一樣、會洩漏規律，所以實際使用時要搭配「模式」，這裡用 **GCM**。

GCM 不是直接拿 AES 加密明文，而是用 AES 產生一長串看起來隨機的金鑰串流，再跟明文做 XOR：

```
計數器區塊:   iv|1    iv|2    iv|3   ...
                │       │       │
              AES(key) AES(key) AES(key)
                │       │       │
金鑰串流:      K1      K2      K3
                ⊕       ⊕       ⊕
明文:          P1      P2      P3
                ═       ═       ═
密文:          C1      C2      C3
```

- iv 是計數器的起點，**key + iv 決定了整條金鑰串流**。iv 不會加進明文裡，明文本身不會被改動。
- 解密時用同樣的 key 和 iv 產生同一條串流，再 XOR 一次就還原，因為 `P ⊕ K ⊕ K = P`。

### iv：同一把 key 下絕對不能重複

iv 不同，同一份明文加密兩次也會得到不同密文，攻擊者看不出「這兩條連結內容一樣」。但更關鍵的是**不能重複**。同一把 key 配同一個 iv，會產生同一條金鑰串流 K：

```
C1 = P1 ⊕ K
C2 = P2 ⊕ K
C1 ⊕ C2 = P1 ⊕ P2      ← K 被消掉了
```

- **明文外洩**：攻擊者不需要 key，就能拿到兩份明文的 XOR；只要猜中其中一份的一部分（例如開頭一定是 `{"name":`），就能推出另一份的對應內容。
- **驗證失效**：攻擊者可以算出 GCM 的驗證金鑰，之後就能偽造通過驗證的密文。

所以 NIST 的規範是：同一把 key，iv 永遠不能重複。常見做法是每次隨機 12 bytes（本專案的做法），或用只增不減的計數器。

## 第三步：tag（防竄改）

只做 XOR 有個弱點：攻擊者看不懂密文，但可以改它。翻轉密文的某個 bit，解密後明文的同一個 bit 也會跟著翻。

GCM 會用 key 衍生出驗證用的金鑰，對密文算出 16 bytes 的 **tag** 附在後面。解密時先重算 tag 比對，不一樣就直接拒絕，連明文都不輸出。

所以本專案的「密碼錯誤」不是靠解出亂碼判斷：密碼錯 → key 錯 → tag 對不上 → `crypto.subtle.decrypt` 直接 throw。連結被改過一個字也會同樣失敗。

## 對照程式碼

```js
// 加密：encodeShare
const salt = crypto.getRandomValues(new Uint8Array(16)); // 隨機 salt
const iv = crypto.getRandomValues(new Uint8Array(12)); // 隨機 iv
const key = await deriveKey(password, salt); // PBKDF2 60 萬次
const sealed = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, bytes); // 密文 + tag
// 連結 = #e= base64url(salt | iv | sealed)

// 解密：decryptShare
// salt = bytes[0..16]、iv = bytes[16..28]、sealed = bytes[28..]
// 同密碼 + 同 salt → 同一把 key；decrypt 先驗 tag，錯就 throw
```

## 為什麼 salt 和 iv 都不是固定值

| | 固定會怎樣 |
| --- | --- |
| salt 固定 | 同一個密碼在所有連結都是同一把 key，攻擊者可以事先建表，一次破解多條 |
| iv 固定 | 同一把 key 重複使用同一條金鑰串流，明文外洩、驗證失效 |

有些範例或舊程式碼會把 iv 寫死（例如全部是 0），那是常見的錯誤寫法，不是慣例。

本專案每次分享都會產生新的 salt，所以 key 每次都不同；就算 iv 不小心重複，也不會跟同一把 key 配在一起，等於多一層保險。不過 iv 仍照規範每次隨機產生，不依賴這層保險。

## 各環節負責什麼

| 環節 | 負責的事 | 擋不住的事 |
| --- | --- | --- |
| PBKDF2 | 把密碼轉成格式正確的 key | — |
| salt | 每條連結都要從頭猜，無法事先建表、無法一次破解多條 | 弱密碼被直接猜中 |
| 60 萬次 | 每猜一次都很慢，暴力猜測成本放大 60 萬倍 | 太常見的密碼還是很快被猜到 |
| iv | 每次加密都用不同的金鑰串流 | — |
| tag | 竄改或密碼錯誤一定會被發現 | — |
| **密碼本身** | **真正的安全來源** | — |

比方說：密碼是鑰匙的齒形；salt 像每間房子的鎖構造都不同，小偷沒辦法先打一把萬用鑰匙到處開；60 萬次像每試一把鑰匙都要等 0.5 秒。但齒形如果是「全平」，小偷對著你家的鎖試幾次還是會開。

## 目前的限制

- **安全程度取決於密碼強度。** 拿到連結的人可以離線暴力破解，介面只提示「建議 8 個字以上」，沒有強制。
- **格式沒有版本號。** 以後要調高次數或換演算法，需要新前綴（例如 `#e2=`）區分，舊連結才解得開。
- **分享對話框的密碼欄是明文顯示。** 刻意讓使用者確認要轉告的密碼沒打錯，但旁邊有人時會被看到。
- **「唯讀」不是權限。** 輸入密碼解開後就拿得到全文。
- **無法撤銷。** 連結送出後，只要有密碼就永遠打得開；要能撤銷得有伺服器。
